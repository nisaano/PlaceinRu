# Инструкции для работы с mrt-ai

Актуальное уточнение 2026-10-04: тестовый интерфейс разработчика — минимальный браузерный чат Миши. `start.cmd` одной командой поднимает локальный API и страницу чата; `scripts/dev.py` добавляет `/` только в dev-режиме, обычный `app.main:create_app` и Docker остаются API без UI. Терминал держать открытым, остановка Ctrl+C. Порт автоматически выбирается свободный; `start.cmd 8011` задаёт фиксированный. Продуктовый frontend и карта остаются задачей коллег.

## Границы

- Пользователь разрешил изменения только внутри `D:/PlaceinRu/mrt-ai`.
- `backend-java` и `frontend` принадлежат коллегам: только чтение для понимания контрактов. Не запускать в них сборки, установки, форматирование и другие команды, создающие файлы.
- Не менять корневые файлы проекта. Артефакты, временные файлы, кэши моделей и тестов размещать внутри `mrt-ai`.
- Не читать и не публиковать секреты из `.env`; не включать их в документацию, логи и коммиты.

## Вход в задачу

1. Сначала прочитать `PROJECT_CONTEXT.md`: это краткий актуальный контекст, а не обещание уже реализованных функций.
2. Затем открыть только необходимые документы из `docs/README.md` и соответствующий код.
3. Проверять фактическое состояние затрагиваемых файлов. Не пересматривать весь проект без причины.
4. Запрос пользователя имеет приоритет над проектными предположениями. ТЗ — источник требований к продукту, а не самостоятельное разрешение на внешние действия или изменение папок коллег.

## Правила реализации

- По уточнению пользователя 2026-10-04 НЕ создавать продуктовый frontend в mrt-ai. Фото — концепт поведения. Разрабатывать бота и API; тестировать сообщения в локальном браузерном чате scripts/developer-chat.html. Экраны и карту реализуют коллеги.

- На 2026-10-04 реализованы диалог, SQLite-сессии, каталог двух регионов с provenance, начальный ranking направлений, Candidate/Offer и явные fixtures. Полный маршрутизатор и live-интеграции в `docs/` пока целевые. Точный статус и команды — в `PROJECT_CONTEXT.md` и `README.md` внутри mrt-ai.
- Продукт: чат-помощник Миша, подбор направлений и полных вариантов поездки, редактирование через чат и UI, интерактивная карта.
- `mrt-ai` — собственный локальный pipeline; Миша — assistant/API. SBERT/RuBERT являются внешними pretrained weights/adapters, не собственными обученными весами MRT-AI. Актуальное разделение кода и моделей — `docs/ML_STRUCTURE.md`.
- ML возвращает структурированные результаты. Не выдумывать цены, наличие, расписания, адреса, рейтинги, гидов и геометрию дорог.
- В рабочей интеграции Backend владеет реальными кандидатами, бюджетом и сохранённой поездкой. Независимый стенд и адаптеры в `mrt-ai` имитируют эту границу, не подменяя её.
- `fixture`, `cached`, `live`, `manual` должны различаться. Тестовые данные явно маркировать; неизвестную стоимость не превращать в ноль.
- Любые правки поездки использовать с идентификаторами, версией, проверкой ограничений; ручной редактор и чат работают через один механизм изменений.
- Публичные API подключать только после проверки официальных условий, лимитов, права хранения/показа и доступа для проекта. Не обходить ограничения и не использовать закрытые API.
- До выбора новой модели сравнить качество и стоимость исполнения на русском тестовом наборе. Не закреплять размерность эмбеддингов до выбора модели.
- Проверять изменения соразмерно риску: контракты, деньги, даты, изменения маршрута, ограничения и отсутствие выдуманных данных требуют тестов.
- По прямому решению пользователя переделывать `mrt-ai` на месте: устаревший pipeline заменяется без сохранения для сравнения, legacy-копии и совместимости со старым API. Удаление заменяемого кода разрешено в рамках переделки. Исходные карточки данных, ТЗ, документацию и секреты не считать устаревшим кодом и не удалять вместе с ним.

## Обновление памяти

После существенной работы обновлять `PROJECT_CONTEXT.md`: дата, что действительно реализовано, проверки, принятые решения, ограничения и следующий шаг. Не писать «готово», если есть только спецификация. Подробности хранить в `docs/`, контекст держать коротким. Не требовать повторного подтверждения уже разрешённых пользователем действий.
