# Дневник изменений mrt-ai

Хронологический журнал заметных изменений реализации. Тестовые данные и модельные оценки явно обозначаются; запись в журнале не означает, что запланированная функция уже готова.

## 2026-10-06

### Blind-review набор и повторная проверка OSM

- Добавлены генератор перемешанного blind-review листа и importer оценок с валидацией 0–3; score, ранги и object ID отсутствуют в листе, answer key хранится отдельно.
- Сгенерирован локальный лист для 6 запросов (54 карточки); проверен import smoke на временных метках. Оценки независимых людей пока не получены.
- Повторная загрузка OSM: Overpass вернул HTTP 504, два fallback завершились timeout. Snapshot отсутствует; источники больше не опрашивались.

### Разделены прямое и тематическое совпадения в ranking

- Исправлен случай, когда общий тег «культура» давал гастрономической прогулке полный матч по запросу «музеи». `trip-fit-bm25-v3` даёт прямому совпадению полный вес, а тематической связи — частичный; она не показывается как `matched_interest`.
- Исключённые интересы теперь фильтруют прямые совпадения. Запрос «гастрономия, исключить музеи» сохраняет гастрономическую прогулку.
- Holdout v1 из шести заранее размеченных сценариев: NDCG@5 0.9915, Recall@5 1.0. В музейном сценарии галерея и музейное пространство ранжируются выше food-walk. Набор synthetic и размечен автором, поэтому это только development evidence.
- Обновлены контракты, planner validator и JSON-схемы. Development v1: NDCG@5 0.9742 / Recall@5 0.9722; holdout v1: NDCG@5 0.9915 / Recall@5 1.0. Полная регрессия: 104 теста PASS.

### Первая оценка trip-fit ranking v2

- Добавлен версионированный набор из 12 synthetic сценариев TripRequest и evaluator с NDCG@5, Recall@5 и разбивкой по группам.
- На текущем fixture-каталоге средние NDCG@5=0.9685, Recall@5=0.9722; multi-interest кейс — 0.8994/0.6667. Разметка создана вручную, показатели отражают только smoke/regression, а не качество на пользовательских запросах.
- Проверено точное перечисление unscored факторов и применение guide=false/исключённых интересов. Полная регрессия: 101 тест PASS.
- Добавлена диагностика неизвестного интереса: API предупреждает, что интерес не повлиял на score и при отсутствии других сигналов порядок карточек нейтральный. Проверка закреплена отдельным API-тестом.
- Расширен evaluator: отдельно считает quality cases и diagnostic cases, показывает попадание релевантных объектов в полный список. В multi-interest сценарии все 6 ожидаемых карточек есть в списке, 4 — в top-5.
- Регрессия после изменения: 102 теста PASS. Слабое ранжирование food-walk в культурном запросе оставлено для blind review; авторской разметки недостаточно для изменения весов.

### Расширено объяснимое ранжирование мест

- Версия ранкера обновлена до `trip-fit-bm25-v2`: тематическое сопоставление покрывает горы, море, озёра, активности, культуру, гастрономию и экскурсии, включая смысловые группы тегов.
- При запросе гида `guide_fit` теперь участвует в score; отказ от гида продолжает исключать гидов.
- Рейтинг и dev-чат явно показывают `unscored_factors`: сезонность, бюджет, вместимость группы и транспорт, если карточки не содержат нужных подтверждённых данных. Так интерфейс объясняет, какие заполненные поля пока не меняют балл.
- Контракты и JSON-схемы обновлены до v2. Независимый benchmark v2 пока не выполнен; этот вариант требует оценки на размеченных запросах, score сам по себе не метрика качества.


### Маршрут из формы на явных тестовых данных

- Dev-чат получил переключатель источника: по умолчанию выбран явно синтетический fixture-каталог; cached OSM остаётся отдельным режимом без fallback. После формы строятся рейтинг и маршрут. В DISCOVER регион выбирается из рекомендаций через versioned API.
- Planner распределяет уникальные места по дням (1/2/3 на день по темпу), не создаёт время поездки и не считает неизвестную стоимость нулём. Синтетические гостиница/транспорт/гид остаются лишь кандидатами.
- Проверено: 101 unit/API тест PASS; браузерные сценарии формы с направлением и без него → выбор региона → демо-маршрут PASS. Реальный OSM snapshot ещё отсутствует.


### Подготовка импорта реальных мест OSM

- Добавлен явный Overpass importer для именованных музеев, парков и ресторанов Москвы и Московской области; кешированный provider выдаёт только загруженный snapshot и не подмешивает synthetic fixtures.
- В snapshot заложены OSM element IDs, ссылки на первоисточник, теги, хеши/временные метки и атрибуция ODbL; UI предупреждает, что актуальность, расписание, цена и наличие не проверяются.
- Nominatim подтвердил для административной Москвы relation 102269; relation 2555133 описывает городскую застройку и не используется вместо административной границы.
- Первый snapshot не получен: Overpass вернул HTTP 504/timeout, в том числе на отдельный запрос музеев. `data/normalized/osm-places.json` не создан; работа с реальными именами остаётся заблокирована успешной выгрузкой. Импортёр не сообщает об успехе и не создаёт пустой/синтетический snapshot.

### Explainable scoring и черновой маршрут по дням

- Добавлен `POST /v1/rank`: запрос TripRequest ранжирует CandidateBatch по BM25-релевантности, покрытию интересов, типу активности и при заданных условиях темпу/семейным тегам. Ответ содержит score 0–100, компоненты, термины совпадений, matched/unmatched interests и причины; явно указано, что score относителен и не является вероятностью.
- Исключённые пользователем интересы применяются как hard filter объектов. Неизвестные цены, наличие и travel time не влияют на score.
- `/v1/route/proposal` использует тот же ranking, добавляет score к пунктам, не повторяет объекты автоматически и показывает пустые дни при недостаточном покрытии. Убраны фиктивные нулевые строки оценочной стоимости; budget summary остаётся incomplete/unknown.
- Dev-чат показывает score и объяснение карточек, затем provisional itinerary по дням; после правок пересчитывает ranking и план.
- Проверки подтверждают изменение top-кандидатов для природы, музеев и гастрономии, фильтрацию исключений, уникальные точки маршрута и отображение score в UI. Данные остаются synthetic fixture; независимая оценка качества ranking ещё требуется.

### Подключение поиска объектов к form-first чату

- Dev-чат после сохранения формы запускает существующий fixture-only BM25 retrieval по региону и интересам и показывает совпадения из attraction/activity/restaurant; поиск повторяется после изменения региона или списка интересов в чате.
- Ответ rules-v1 при уже выбранном регионе больше не просит пользователя выбрать направление ещё раз. В сообщении явно указано, что полный маршрут, live-услуги и стоимость пока не сформированы.
- Выдача явно обозначена как синтетическая: маршрут не строится, цена/доступность неизвестны, вымышленные координаты и расписания не подходят для реальной навигации.
- Браузерный smoke на форме Москва → Московская область с интересами «природа, музеи, гастрономия» показал пять demo-кандидатов, совпадающих по словам интересов. Полная регрессия после изменений: 91 unittest PASS.

### Структурированная форма маршрута в dev-чате

- Браузерный dev-чат переведён на form-first сценарий: свободное поле выключено до отправки начальных требований формой; после этого текстовое поле используется для правок собранной поездки.
- Форма по концепту включает календарную дату начала, длительность, origin/destination с режимом подбора, состав группы 1–4, детей, категории интересов, гида и бюджет с явными basis/period.
- Отправка сохраняет нормализованные поля `TripRequest` через существующий session API; пустые необязательные значения явно сбрасываются. В интерфейсе можно раскрыть точный JSON `updates`, отправленный API.

- Форма не изображает NLP-извлечение: структурные значения поступают напрямую, а свободный текст тестируется отдельно через rules-v1/RuBERT. Реальный каталог по-прежнему ограничен имеющимися fixture регионами.

- Последний synthetic test: RuBERT macro/micro F1 0.6266/0.6885, exact match 0.2963; rules-v1 — 0.7797/0.7937 и 0.7037. Это крошечный синтетический smoke-test, не оценка реального качества; classifier не управляет ответом или состоянием поездки, правила остаются parser Миши.

Сравнительный endpoint включён только в `scripts.dev`, модель загружается лениво. Недоступность checkpoint/dependencies показана явно, не мешает rules-v1 диалогу.

### Локальный SBERT embedding retrieval

- Добавлен опциональный `ranking_method: "embedding"` в `POST /v1/search/places`; BM25 остаётся default и не требует ML runtime. Для embedding используется `ai-forever/sbert_large_nlu_ru`, закреплённый commit revision `89deeaa197d9d146e5763ac1f5fe32bf66817126`, CPU inference и masked mean pooling с нормализацией векторов.
- Добавлены optional `requirements-ml.txt` и `scripts.download_embedding_model`. Скачиваются только нужные tokenizer/config файлы и `model.safetensors` (1,707,679,808 bytes); SHA-256 проверяется до записи локального model manifest. Модель хранится в игнорируемой Git-папке `models/`; API ничего не загружает из сети. Если model/dependencies отсутствуют, запрос получает явную ошибку 503, без незаметного BM25 fallback.
- Добавлен lazy loader, небольшие inference batches, ограниченный cache эмбеддингов synthetic candidates и сравнение BM25/embedding в `scripts.evaluate_retrieval`; embedding отчёт включает NDCG@5, Recall@5, MRR и CPU latency после model warmup. Полный набор: 77 unit/API тестов PASS, включая стабильную сортировку/кэш, schema и явную недоступность модели.
- Ресурсы машины: CPU-only PyTorch установлен в `mrt-ai`; на D: свободно около 323.6 GB, установленная RAM — около 15.7 GB. Закреплённый snapshot проверен по SHA-256; действительный embedding маршрут API проверен локальным запросом.
- Первый корректный прогон на 8 synthetic queries: SBERT NDCG@5=0.8577, Recall@5=0.8542, MRR=1.0000; BM25 NDCG@5=0.9031, Recall@5=0.8958, MRR=1.0000. SBERT в этом крошечном наборе уступил лексическому baseline, поэтому BM25 остаётся default. После warmup CPU latency embedding query: mean 240.7 ms, p50 228.8 ms, p95 284.3 ms; подготовка модели и candidate vectors заняла 22.25 s. Это только локальная техническая оценка.
- Все catalog candidates и judgments остаются synthetic. Эти smoke-метрики не являются внешней оценкой; модель не обучалась и не строит проверенные маршруты.

### Локальный поиск по объектам: BM25 baseline

- Добавлен endpoint `POST /v1/search/places` для поиска по объектам выбранного региона. Нужен явный `data_mode: fixture`; выдача содержит только записи с synthetic provenance.
- Реализован воспроизводимый лексический ранжировщик BM25 (`bm25-lexical-v1`) с полями названия, тегов и описания; в ответ включены score и совпавшие нормализованные термины. Это baseline, не embedding-модель.
- Добавлен небольшой вручную размеченный синтетический набор `data/fixtures/search-relevance.json` и evaluator `python -m scripts.evaluate_retrieval`, считающий NDCG@5, Recall@5 и MRR.
- Последний локальный прогон baseline: 8 smoke-запросов, mean NDCG@5 = 0.9031, mean Recall@5 = 0.8958, MRR = 1.0000. Метрики измерены на синтетических запросах о синтетических объектах, созданных в одном проекте; это регрессионная проверка, не независимая оценка и не доказательство качества на пользовательских запросах.
- Ограничения: нет семантического сопоставления перефразировок без общих слов, модели/эмбеддингов, реальных POI, географической сортировки, маршрутизации, проверки расписаний, цен или доступности.

### Подготовка предыдущего ML эксперимента

- Рассмотрен [ai-forever/sbert_large_nlu_ru](https://huggingface.co/ai-forever/sbert_large_nlu_ru): официальный model card описывает русскоязычные sentence embeddings и mean pooling; Hugging Face metadata указывает MIT и 426,908,672 параметра. Модель тяжёлая для CPU. Рассмотрен также [sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2): multilingual embedding model, 384 dimensions и Apache-2.0 по model metadata. Качество на PlaceinRu не измерялось.
- Выбрана SBERT модель, но до реализации настоящего encoder и закрепления snapshot её векторы ещё не вычислялись; runtime зависимости присутствовали в project venv. Теперь следующий самостоятельный шаг — отделённый, более крупный русскоязычный evaluation набор и данные для intent classification.
