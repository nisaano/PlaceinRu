# Продуктовая спецификация: Миша

Тестовый интерфейс разработчика — минимальный браузерный чат Миши. `start.cmd` поднимает локальный API и открывает страницу; `scripts/dev.py` добавляет `/` только в dev-режиме. Обычный API и Docker не включают UI. Продуктовый frontend и карта остаются задачей коллег.

Уточнение пользователя 2026-10-04: в mrt-ai разрабатываем бота и HTTP API, без продуктового frontend. Фото — концепт поведения. Экраны и карта принадлежат frontend коллег. Тестовый интерфейс — минимальный браузерный чат scripts/developer-chat.html. Возвращаем текст и JSON.

## Цель и границы

Чат помогает выбрать и изменить целую поездку по России. Основной результат — несколько сравнимых вариантов с понятными ограничениями, затем выбранный маршрут по дням и карта. «Оптимальный» означает лучший среди доступных кандидатов по заданным критериям; глобальная оптимальность не обещается.

Вариант включает регион, транспорт туда/обратно, размещение на нужные ночи, локации, рестораны, активности и опционального гида. Для предложений показываются источник, актуальность, состав цены и ссылка перехода. Если категория недоступна, это явно указано, а вариант получает статус неполного. Оплата, покупка билетов и отправка заявки гиду происходят на внешнем сайте по действию пользователя.

На 2026-10-04 через API работают диалог, изменение параметров и подбор Москвы/области. Синтетические объекты доступны по явному запросу fixture. Подбор реальных услуг, полные варианты и карта ниже описывают целевой продукт. Продуктовый frontend коллег не меняется.

## Сценарии

1. Пользователь задаёт отправление, направление или просьбу подобрать его, диапазон дат, интересы, общий размер группы и наличие детей. Бот извлекает слоты из текста и полей формы, коротко уточняет критичные пробелы, помнит предыдущие ответы. Бюджет, темп и транспорт можно добавить, но они не блокируют первичный подбор региона.
2. `DISCOVER`: пользователь не знает, куда ехать, или просит предложить регион. Система предлагает до трёх разных направлений с объяснением и уровнем полноты данных. Не спрашивает «куда?» как обязательный вопрос этого режима.
3. `PLAN`: направление выбрано. Получаются реальные кандидаты для заданных дат/группы, формируются до трёх вариантов поездки; если подходит меньше — возвращается меньше.
4. Выбор варианта открывает дни, карту, бюджет и ссылки. Пользователь может закрепить понравившиеся элементы.
5. «Отель дешевле, экскурсию второго дня убери, вместо неё прогулку, бюджет не увеличивай» формирует несколько структурированных операций. Бот уточняет только неоднозначную цель изменения.
6. Ручное редактирование делает те же операции: заменить/добавить/удалить/перенести/закрепить. Обе формы редактирования обновляют одну версию поездки.
7. Перед применением рассчитываются последствия: цена, доступность, время, изменённые элементы. Если ограничения нарушены, показывается причина и альтернатива; предыдущая версия остаётся доступной.
8. Сохранение рабочей поездки делегируется Backend. На автономном стенде — локальный черновик и экспорт JSON, с явным обозначением режима.

## Параметры

- Откуда: населённый пункт и канонический ID; аэропорт/вокзал уточняется при необходимости.
- Направление: region/city/place ID либо явное разрешение подобрать.
- Даты: начало и конец или начало + длительность; календарные даты передаются как ISO `YYYY-MM-DD`. Одно слово «летом» не достаточно для живых предложений. Относительные даты считаются относительно переданных `reference_datetime` и timezone пользователя.
- Бюджет: сумма, валюта, на всю группу или человека, на всю поездку или сутки, что включено, жёсткость ограничения. Для MVP расчёты в RUB; иную валюту нельзя молча трактовать как RUB.
- Группа при первичном подборе: общее число путешественников и ответ, будут ли дети. Если ответ «да», точное число и возраст детей остаются неизвестными и запрашиваются только перед услугой/тарифом, которым они необходимы.
- Интересы/активности и формат: городской/природный/пляжный и др.; темп, комфорт, ограничения мобильности при наличии.
- Транспорт: допустимые способы, туда/обратно, время отправления, пересадки, багаж при необходимости. Ответ «любой» — известное значение, не пропуск.
- Гид: нужен/не нужен/не определено, специализация, язык, даты, бюджет.

Неизвестное хранить как unknown/null, явный отказ отдельно. Не домысливать детей=0, группу=1 и сумму «на всех». Допускается объединить связанные пробелы в один короткий вопрос. Если пользователь отказался уточнять бюджет, темп или транспорт, можно дать обзор направлений без обещания тарифа и бюджета.

## Интерфейс стенда

Визуальный ориентир пользователя и поведение десяти панелей описаны в [CHATBOT_CONCEPT.md](CHATBOT_CONCEPT.md). Концепт дополняет сценарий карточками «Комфорт / Баланс / Бюджет», сводкой уточнений, деталями по категориям и объяснением изменений; его экраны оплаты адаптируются к внешним ссылкам, без собственного checkout.

Desktop: чат слева, сравнение вариантов и план справа, переключаемая карта. Mobile: вкладки «Чат», «Поездка», «Карта». Общая панель параметров и переключатель fixture/live видны постоянно.

В карточке варианта: регион, транспорт, отель, дни, еда/активности, гид, известная стоимость и неизвестные статьи. Отдельно доступны объяснения выбора, время проверки цены, «Выбрать», «Изменить», «Перейти к бронированию». Устаревшее предложение требует перепроверки, переход по ссылке не равен бронированию.

Карта: номера остановок, цвет дня, маршруты между точками, тип перемещения, время/расстояние при наличии источника. Выбор точки выделяет карточку и наоборот. Фильтр дней, масштабирование по маршруту, легенда и атрибуция. Линия без дорожной геометрии только пунктирная с подписью «схема перемещения».

Состояния UI: уточнение, поиск, частичный результат, нет подходящих вариантов, таймаут источника, устаревшее предложение, конфликт версии, превышение бюджета, ошибка сохранения. Ручная правка не исчезает после следующего сообщения. Все действия доступны клавиатурой; ошибки отражаются текстом.

## MVP и расширение

Первый срез: Москва/область, русский язык, RUB, одна группа, одна выбранная база размещения, последовательные дни, один необязательный гид. Это проектное допущение, его можно поменять до подготовки каталога. Даты проживания и обратный транспорт обязательны для полного варианта. Затем межгородские сценарии с поездом и самолётом для направлений с подтверждённым покрытием данных.

Не входит в первую версию: собственный checkout, автоматическое бронирование, обучение большой генеративной модели с нуля, коллаборативная фильтрация без истории, обещание покрытия всей России и глобально оптимального маршрута.
