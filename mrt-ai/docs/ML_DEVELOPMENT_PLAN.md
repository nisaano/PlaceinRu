# План разработки ML-системы PlaceinRu

Обновлено: 2026-10-06. План относится к каталогу `mrt-ai`. Пользовательский frontend, карта, авторизация и бронирование разрабатываются другими компонентами. Минимальный dev-чат — только стенд для проверки API.

## Цель и принципы

Миша принимает форму поездки и сообщения, уточняет недостающие параметры, подбирает объекты, ранжирует их и строит маршрут-предложение в JSON. Все факты должны ссылаться на конкретный источник данных. Неизвестная цена, вместимость, график или время переезда остаются неизвестными. Синтетические fixtures доступны только при явном `data_mode=fixture`.

Вероятностная обработка языка и детерминированные решения разделены. Pydantic проверяет вход и результат; ограничения и изменение состояния проверяются серверным кодом. Новую модель подключать только после сравнения с baseline на размеченном наборе. LLM-провайдер пока не выбран и не нужен для запуска стенда.

## Приоритеты и этапы

### 1. Зафиксировать качество ранжирования v2 — следующий шаг

Сформировать небольшой, явно синтетический, но полный набор сценариев формы: сочетания интересов, темп, наличие детей, запрос/отказ от гида, неподдерживаемая категория и запрет интереса. Для каждого запроса вручную определить ожидаемый порядок или допустимые диапазоны и причины. Измерять NDCG@K/Recall@K, отдельно проверять стабильность объяснений и отфильтрованные объекты. Не использовать эти данные как реальные пользовательские метрики. Сравнить с предыдущим сохранённым baseline либо вручную зафиксированным результатом; не менять holdout после просмотра ошибок без повышения версии.

**Готово, когда:** score-компоненты соответствуют ожиданиям набора, веса суммируются к 1, исключённые интересы не попадают в выдачу, обязательный гид меняет релевантность только категории GUIDE, неизвестные параметры не превращаются в штраф или бонус. Версию ранжирования и результат оценки записать в `docs/EVALUATION.md`.

### 2. Профиль интересов и надёжность признаков

Определить закрытый начальный справочник категорий и версионированное отображение тегов каталога на категории. Хранить отдельно явные предпочтения, отрицания и неизвестные категории. Явные веса пользователя поддержать в контракте; не выводить отрицательный интерес из отсутствия упоминания. Оценки модели и нормализованные ручные поля различать по происхождению.

**Готово, когда:** один и тот же запрос и snapshot дают воспроизводимый профиль; объяснение каждой оценки перечисляет использованные совпадения; неизвестная категория не считается неприятием.

### 3. Данные мест пилота

Проверить получение первого ограниченного OSM snapshot для Москвы/области либо выбрать допустимый доступный источник/ручной каталог с provenance. Включить имена, категории и координаты; сохранять source ID/URL, лицензию, время получения и поля исходника. OSM-тег часов работы не равен подтверждённому текущему расписанию. Не заполнять цены и вместимость предположениями. Для fixture-каталога отдельно добавить признаки под тесты season/capacity/transport только с явной маркировкой синтетики.

**Готово, когда:** cached API возвращает реальные source-backed кандидаты, повторный импорт воспроизводим, отсутствие snapshot — явная ошибка, автоматического fixture fallback нет.

### 4. Подбор и диверсификация

Разделить жёсткие фильтры (регион, отрицания, подтверждённая недоступность) и мягкие предпочтения. Развить тематическое покрытие и калибровку score на оценках relevance. Добавить разнообразие категорий и ограничить повторяющиеся типы в top-K после измерения влияния. Вводить сезон, бюджет, вместимость и транспорт в score только после появления релевантных полей кандидата; в ином случае сохранять `unscored_factors`.

**Готово, когда:** есть отчёт per-interest/per-category, top-K не состоит случайно из почти дубликатных записей и ни один обязательный фильтр не нарушен.

### 5. Планирование с проверенными ограничениями

До сложной оптимизации определить port матрицы времени и поставщика окон работы. Преобразовать часы работы в доступные интервалы с учётом timezone и даты. Рассчитывать визит и перемещение только из входных данных провайдера. Затем выбрать простой алгоритм планирования; оценить OR-Tools, если количество ограничений и объектов это оправдывает. Учитывать бюджет только при известных суммах и основаниях тарифа.

**Готово, когда:** маршрут проходит независимый validator, имеет ноль нарушений hard constraints на приёмочных сценариях; неизвестные сегменты помечаются, а неполный план не называется validated.

### 6. Обучаемые компоненты

Собирать разрешённые и обезличенные пользовательские формулировки с эталонными слотами, intent и неоднозначностью. Делить данные по диалогам и семействам фраз; удерживать независимый test. Сначала улучшить slot extraction/intent только там, где есть измеренная ошибка. SBERT оставлять как retrieval-кандидата и включать только при измеримом выигрыше против BM25. Проверять стоимость, задержку, качество по классам и поведение при низкой уверенности.

**Готово, когда:** кандидат лучше baseline на независимой выборке и критические ошибки (даты, суммы, negation, назначения) проходят отдельные safety-пороги. До этого `rules-v1` остаётся production parser.

### 7. Структурированные объяснения и правки

Сначала генерировать explanations из проверенных `reasons`/score-компонентов. После появления стабильного маршрута спроектировать `ChangeSet` preview/apply с ID цели, expected version и повторной валидацией затронутых дней. LLM может извлечь команду, но применение и ограничения остаются детерминированными.

**Готово, когда:** текст не добавляет фактов вне кандидатов и плана; изменение сохраняет закреплённые точки и атомарно отклоняется при конфликте или невозможности.

### 8. Интеграция и выпуск

Согласовать с Backend envelope, идентификаторы, единицы денег, владельца реальных кандидатов и маршрутных операций. Проверить JWT, таймауты, ошибки и сохранение лишь после готовности интерфейса коллег. Dev fixtures исключить из production. Отдельно собирать offline-качество, задержку, долю partial/no-candidate и пользовательскую обратную связь с необходимыми правами.

## Зависимости

```text
Верный benchmark score v2 ──→ профиль признаков ──→ расширенный каталог
                                                   └─→ оценка retrieval/ranking
Каталог + окна + travel matrix ──→ валидируемый planner ──→ ChangeSet
Размеченные реальные фразы ──→ улучшение NLU (только если baseline проигрывает)
Стабильные контракты ──→ интеграция с Backend/frontend коллег
```

Открытый OSM источник может улучшить поиск мест, но сам по себе не предоставляет билетную цену, наличие, бронирование или дорожное время. Эти категории требуют отдельного подтверждённого источника или остаются пустыми/неизвестными.

## Отдельно оцениваемые ML-эксперименты

- Intent: macro/per-label F1, exact match против `rules-v1` на новом семейном holdout.
- Слоты: per-field P/R/F1 и exact match нормализованного состояния; отдельно даты, деньги, числа, неизвестное и отрицания.
- Retrieval: BM25/SBERT NDCG@5, Recall@5, MRR, latency на одинаковых query/candidate snapshots.
- Trip-fit ranking: NDCG@K/Recall@K, per-category и coverage интересов, влияние diversity reranking.
- Planner: hard-constraint violation rate, покрытие выбранных дней, оценка полезности человеком; `provisional` и `validated` анализировать раздельно.
- Система: end-to-end completion диалогов, повторные уточнения, latency API, стоимость только при подключении платной модели.

## Размещение кода

Текущая структура `app/` для API/диалога и `mrt_ai/` для pipeline подходит; дублирующую директорию `ml/` не создавать. Dataset остаётся в `data/datasets/`, fixtures — в `data/fixtures/`, скрипты воспроизведения — в `scripts/`, контракты — в `mrt_ai/contracts/`, eval-отчёты — в `docs/EVALUATION.md`.
