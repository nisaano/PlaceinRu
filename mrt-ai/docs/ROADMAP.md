# План переделки

Тестовый интерфейс разработчика — минимальный браузерный чат Миши. `start.cmd` поднимает локальный API и открывает страницу; `scripts/dev.py` добавляет `/` только в dev-режиме. Обычный API и Docker не включают UI. Продуктовый frontend и карта остаются задачей коллег.

Уточнение пользователя 2026-10-04: в mrt-ai разрабатываем бота и HTTP API, без продуктового frontend. Фото — концепт поведения. Экраны и карта принадлежат frontend коллег. Тестовый интерфейс — минимальный браузерный чат scripts/developer-chat.html. Возвращаем текст и JSON.

Статус 2026-10-04: реализован первый диалоговый срез этапов 1–2 и части этапа 3: импорт двух карточек регионов, аудит 226 строк, ranking, выбор региона, read-only Java trips adapter и явный synthetic fixture-каталог из 17 объектов шести категорий для двух регионов. Локальный SBERT embedding retrieval и BM25 baseline реализованы. Добавлен multi-label intent training pilot на 135 синтетических сообщениях с RuBERT-tiny2; результат пока хуже rules-v1. Локальный developer chat показывает обе классификации рядом, но ответы и изменения поездки по-прежнему формирует rules-v1. Добавлен benchmark извлечения восьми параметров поездки: rules-v1 улучшен на ошибках, замеченных при первом тесте; новая синтетическая контрольная выборка 15/15 проходит exact match. Это тест интерфейса правил, а не обученная slot-модель или реальная независимая оценка. Проверка реального Backend с JWT не выполнена. Фактический запуск — `../README.md`, детали — `CATALOG.md` и `EVALUATION.md`.

## 0. Основа и границы

Результат: замена устаревшего кода новой структурой непосредственно в `mrt-ai`, воспроизводимое окружение, изолированные порты/БД и правила секретов. По решению пользователя старый pipeline не сохраняется для сравнения и не поддерживается параллельно. Зафиксировать предложенный пилот Москва/область и минимальный межгородской сценарий. Уточнить бюджет как общий/на человека и оборудование при реализации, не угадывать мощность GPU.

Приёмка: новые команды не записывают ничего в папки коллег; исходные карточки данных и документы сохранены, устаревший код и ненужные производные кэши заменены без legacy-копий; документация отличает реализованное от планов. Проверка доступа провайдеров идёт независимо, без обязательного ожидания ключей для разработки.

## 1. Контракт, taxonomy и примеры

Результат: Pydantic/JSON Schema для TripRequest, state, intents, Candidate/Offer, RouteProposal, BudgetSummary, MapResult, ChangeSet и feedback. Синтетические примеры happy/error/partial; mapping Java полей; canonical IDs и теги.

Приёмка: схемы проверяют все примеры; невалидные даты, деньги, unknown значения и недопустимые операции отклоняются; поля версии обязательны. Разница с Java выписана для коллег. Согласование production-контракта ещё требуется, но разработка независимого стенда продолжается.

## 2. Диалог и самый ранний пользовательский стенд

Результат: parser/intent baseline, reducer слотов, DISCOVER/PLAN, missing parameters; HTTP API диалога и браузерный dev-чат. Сначала без модели генерации и без внешних предложений.

Приёмка: пользователь проходит 5–10 сообщений, ответы не теряются, исправления имеют приоритет, повторных ненужных вопросов нет. Понимаются составные правки и отказы; отсутствие направления в DISCOVER не блокирует подбор. Сохраняется отдельная сессия; есть restart/reset.

## 3. Каталог и порты данных

Результат: импорт карточек Москвы/области с проверкой качества, каталог объектов с provenance, разрешённые источники координат; fixture adapters всех категорий; интерфейсы Backend/провайдеров, routing и budget. Реестр API из PROVIDERS заполняется фактическими результатами проверки.

Приёмка: плохие строки не теряются молча, дубли выявляются, каждый объект имеет стабильный ID и источник; fixture не смешивается с live. Отсутствие API даёт partial, а не выдуманное предложение. Неизвестная цена остаётся неизвестной.

## 4. Ranking и embeddings

Результат: фильтры ограничений, объяснимый baseline, сравнение энкодеров и лексического поиска, выбор модели/размерности, pgvector и манифесты индекса, переиндексация. Для intent классификации и извлечения слотов существуют synthetic pilots (см. EVALUATION). Следующий ML шаг — собрать и обезличить реальные пользовательские формулировки, разметить normalized slot values и расширить независимый holdout; затем обучить кандидата slot extractor и сравнить его с rules-v1 по per-field/end-to-end exact match. Набор вариантов с различиями по стоимости/комфорту/активностям.

Приёмка: не проходят жёсткие запреты, scores воспроизводимы, выбор объясняется признаками; новый поиск сравнивается на замороженном наборе. Проверены смена модели/корпуса, rollback индекса и отсутствие смешения embeddings.

## 5. Поездка по дням, бюджет и карта

Результат: планировщик по окнам времени и travel matrix, budget calculator стенда, validation port, отель на нужные ночи, транспорт туда/обратно, опциональный гид; структурированные дни, точки и GeoJSON для frontend коллег.

Приёмка: можно выбрать вариант и увидеть все шесть категорий результата либо явную причину отсутствия; нет конфликтов в маршруте со статусом validated. Бюджет правильно учитывает группу, ночи, комиссии и исключает двойной счёт. На карте различаются routed и schematic; нет выдуманного времени дороги.

## 6. Редактирование через чат и вручную

Результат: ChangeSet preview/apply, версии, идемпотентность, закрепление, undo; замена отеля, удаление/добавление активности, изменение дат/бюджета/транспорта/гида, перестройка затронутых дней.

Приёмка: одинаковая ручная и текстовая операция дают одинаковое состояние; конфликт 409 не теряет правки; пакет изменений атомарен; после смены дат старые тарифы не выглядят свежими. Неоднозначная цель вызывает уточнение, а невозможная правка объясняется без повреждения маршрута.

## 7. Реальные источники и интеграция

Результат: минимум один подтверждённый источник на необходимую категорию пилота либо честно ограниченное покрытие; booking/search/inquiry links; smoke проверки и мониторинг квот. Backend adapter реализуется в `mrt-ai`; необходимые изменения Java и основного frontend оформляются как отдельный контракт для коллег.

Приёмка: источник и время проверки видны, условия использования задокументированы, ключи не попадают в клиент; в live-режиме нет fixtures. Для полного пилота подтверждены транспорт, размещение и остальные обязательные затраты. Реальные маршруты проверяет интегрированный Route Engine. Production-сохранение проверяется совместно с Backend, не объявляется готовым по локальному mock.

## 8. Evaluation, feedback и выпуск

Результат: оценочный отчёт, метрики и регрессии, обработка событий, эксплуатационные команды, ограничения покрытия, документация API и воспроизводимый запуск новой системы. Сбор/аннотация тестов начинается на этапе 1, проверки выполняются на каждом этапе; здесь финальная приёмка.

Приёмка: критерии EVALUATION выполнены на замороженном наборе, имеются отчёты на указанном оборудовании; инструкция позволяет воспроизвести демо с нуля. Устойчивы offline, timeout, пустой каталог и unknown стоимость. Обновлены PROJECT_CONTEXT и инструкции запуска. Система не зависит от старого pipeline, заменённого в начале переделки.

## Решения, которые уточняются при реализации

Предложения по умолчанию: Москва/область, русский язык, RUB, до трёх вариантов, браузерный dev-чат, отсутствие обязательного платного LLM. Пользователь может изменить их. Не блокировать подготовку контрактов из-за выбора дизайна UI или конечной модели.

Внешние зависимости: выдача ключей/партнёрского доступа, право на данные, согласование production DTO и наличие Route Engine у Backend. Недоступность этих зависимостей ограничивает live-приёмку, но не мешает этапам 1–6. Никаких сообщений коллегам, регистраций и платных подключений в рамках этого плана автоматически не выполнять.
